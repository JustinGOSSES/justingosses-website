## Executive Summary

Modern software is built on layers of open source code written by others—these are called dependencies. While dependencies speed up development, they also introduce risks: security vulnerabilities, abandoned projects, or even malicious code that can end up in your application. Companies often use paid enterprise security tools to catch these problems, but these tools typically apply one-size-fits-all rules across all projects and focus primarily on known vulnerabilities and license compliance risk and miss sustainability risks like abandoned packages or projects at risk of sudden maintainer departure.

This post explores using "instruction files" to guide GitHub Copilot (an AI coding assistant) to automatically research and report on dependency risks right in your editor, before you ever use a new package. The result is a detailed, scannable report that helps developers make informed decisions—catching potential problems at the cheapest possible moment: before code is written.

This approach won't replace paid enterprise security tools—it lacks enforcement mechanisms, isn't deterministic, and has no good distribution method across many repositories. However, it offers two compelling advantages: flexible, project-specific thresholds for acceptable risk levels, and better identification of sustainability risks that traditional tools often ignore. For developers in large companies who want to make more informed dependency choices beyond what their compliance-driven security tools provide, or individual developers who want some risk filtering without paying for enterprise-level tooling, this instruction file approach might offer an appealing complement to existing practices.

## What are dependency risk instruction files?

Instruction files are markdown files in a code repository that customize
[GitHub Copilot](https://docs.github.com/en/copilot) responses. While
[agent.md](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/create-custom-agents?versionId=free-pro-team%40latest&productId=copilot)
customizes Copilot behavior when explicitly called, instruction files are 
in a sense always "on", though there can be a "description" field defined
at the top of them that described when the instructions should be used.
For a more in-depth introduction to instruction files, see [the GitHub Copilot docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions).

Dependency risk instruction files are designed to provide detailed guidance for Copilot,
when in agent mode, on where to get information and how to assess the risks of using a
third-party package or library in software development, as well as how to format that
information into a standardized dependency risk report in the chat window that is
easily scannable and understandable by developers such that they make better informed
decisions about dependency consumption. This improves GitHub Copilot behavior on
these tasks considerably. It also helps avoid the
[problem of AI assistants recommending non-existent dependencies](https://www.theregister.com/2024/03/28/ai_bots_hallucinate_software_packages/), or even worse, dependencies that were created as by malicious actors.
Any packages with few to no downloads produce a risk report with many red flags.


## But wait...What do we mean when we say "less risky dependencies"?

Less risky dependencies are those that have been evaluated and found to have a lower
likelihood of introducing security, legal, or maintenance related problems.
These problems have cost in terms of both direct security, legal, and reputational
impact as well as indirect operational cost of dealing with them later.

#### Type of risk:
- Malicious code:
    - _"Code that was written in ways to do or enable malicious actors"_
- Vulnerabilities:
    - _"Code accidentally written in ways that can be exploited by malicious actors"_
- Poor security posture:
    - _"Code that is not vulnerable but at high risk of project take over, malicious code being snuck in, sabotage, etc."-
- license risk:
    - _"Code that does not have an open source license that would enable its use in the manner it is being used or that goes against company policy"._
- Sustainability risk:
    - _"Code that built by a community that is of most risk now or in future of not meeting implicit expectations around respond to issues or pull requests for security problems, new features, bug fixes, etc."_

#### Recognition of risk can be occur via:

- Metadata:
    - Become aware of known vulnerabilities (CVEs), often in specific versions.
    - license compliance issues
    - Generate a picture of community activity and related sustainability risks
- Scans packages or package source repositories for:
    - unknown security vulnerabilities
    - malicious code
    - license compliance issues
- Manual review of dependency documentation and community activity
    - Vulnerabilities
    - Security posture
    - Sustainability risks

The active scans in the second bullet point are largely only available from
paid tooling, though sometimes tools are free for open source licensed public
repositories.

While anyone could manually review each dependency before use, few developers can
say they're ever evaluated the security and community health of every dependency
in a single project.

#### When do developers become aware of dependency risks?

When developers become aware of dependency risks is highly dependent on the
tooling they use to detect risks. 

- Before writing any code:
    - This might occur if they are doing manual web research into the safety of a possible new dependency.
- When they write code in their IDE:
    - If they have leveraging an IDE extension to evaluate dependency risk.
- When submitting a pull request that contains the new dependency:
    - Many paid SAST (Static Application Security Testing) tools operate as a CI/CD check.
- After code is merged at some regular time interval:
    - Dependabot operates like this.

#### Types of actions that can be taken regarding dependency risks:

- Decide to not start using the dependency
- Blocked from merging a pull request with the dependency
- Replace after initial use with another dependency or their own code
- Update after initial use (for vulnerabilities that only impact a specific version)
- Take action to improve sustainability of the community developing the dependency
    - Upstream contribution, usually code contribution
    - Financial contribution, usually via Open Collective or GitHub Sponsors

To effectively take action before a dependency has been used, requires the information to
be presented to the developer at the time they are first using the dependency or during
evaluation of a dependency. This effectively means either tooling integrated into their
IDE or a website they leave their IDE to looked at for guidance information.
It is cheaper to not start using a dependency than it is to swap it out later,
update to a different version, or take actions to improve the sustainability
of the project.

## Enterprise SAST Tooling to flag dependency risks

There are a varity of enterprise tools that can help developers recognize and reduce
dependency risks. These tools often integrate into the developer's IDE or CI/CD pipeline
to provide real-time feedback on the dependencies being used. 
A web search of "Popular SAST tools" returned:
- [Snyk](https://snyk.io/)
- [WhiteSource](https://www.mend.io/)
- [Black Duck](https://www.blackduck.com/)
- [Sonatype](https://www.sonatype.com/)
- [FOSSA](https://fossa.com/)
- [GitHub Advanced Security](https://docs.github.com/en/get-started/learning-about-github/about-github-advanced-security)

### SAST tools' main strength/weakness is that they are focused on compliance 

These tools are largely pitched at Enterprise's rather than individual developers
for the most part. As a result, they are focused on company-wide compliance rather
than risk reduction that takes into account each repository's needs and constraints.
This compliance perspective means SAST tools typically aren't great at types of risk
where not every repository would have the same cut off for what is acceptable.

### Differences Between Binary and Continuous Dependency Risks

It can be helpful to think of dependency risks in terms of two classes of dependency risks, continuous and binary.
Binary risks are either present or not, with clear yes/no answers, which makes them fit well into compliance frameworks
and compliance tooling that can be deployed across an entire organization with the same thresholds and rules.
Continuous risks in contrast are risks that tend to exist on a continuous spectrum of risks and different projects
can reasonably have different thresholds for what is acceptable risk.

| Risk Class  | Definition                                                                 | Impact Felt At What Scale | Impact Types                        | Risks Best Addressed By What Type of Framework?         |
|-------------|----------------------------------------------------------------------------|--------------------------|-------------------------------------|---------------------------------------------------------|
| Binary      | Risks that are either present or not, with clear yes/no answers.            | Company-scale            | $, reputation, trust                | compliance frameworks                                    |
| Continuous  | Risk presence is a continuous spectrum. Always some risk.                   | Individual team          | unplanned for developer time        | risk-reduction frameworks                                |

### Types of dependency risk considered by the dependency risk report

| Risk Class    | Risk                      | Definition                                                                 | Factors Considered in Report                                                                                 |
|---------------|---------------------------|----------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------|
| Binary        | Vulnerability             | Whether known security vulnerabilities are associated with the dependency based on a CVE.        | Report uses public vulnerability databases reflected in ecosyste.ms. and sometimes vulnerability information on source repository in GitHub. Use other tools for full assessment!                        |
| Binary        | License                   | License of the package.            | Currently, only the first identified licenses is surfaced to the user.  Does not cover multiple licenses, modified licenses, whether copyleft license, tell you what licenses require extra steps, etc. Use other tooling for actual license compliance!              |
| Binary        | Malicious                 | Whether the package contains known or suspected malicious code.               | Currently, this does nothing but tell you to use your own tooling and check for company instructions file for listed tooling. It is a placeholder.       |
| Continuous    | Possibly abandoned _(sustainability)_        | Assesses if the dependency appears to be no longer maintained.              | Considers time since last release, lack of recent activity, if source repository is archived, etc.               |
| Continuous    | Not enough eyeballs _(sustainability)_     | Evaluates if there are too few contributors or reviewers to catch issues.   | Considers number of downloads, number of dependent repositories.                   |
| Continuous    | Contribution could stop suddenly _(sustainability)_ | Considers the risk that development may halt unexpectedly.           | Considers reliance on a single maintainer, if number of contributors is small, if only single version published, too few commits recently, etc.  |
| Continuous    | Poor security posture     | Assesses the overall security posture of the project.  | Considers low OpenSSF Scorecard score, if uses a dangerous GitHub Action workflow pattern, etc. Note that not all packages will have pre-existing scans by OpenSSF Scorecard |

#### What parts of continuous risk can be assessed well with publicly available metadata alone as these instructions try to do?

Continuous risks can be thought of as including three partially overlapping categories:
sustainability risks, quality risks, and security posture risks.
Sustainability risks can include "Possibly abandoned", "Not enough eyeballs to spot bugs", and
"Contribution could stop suddenly". While sustainability risks are often possible to identify with
package and source repository metadata publicly available in 2025 as they are largely activity-based
and community-based measurements, quality risks and security posture risks often require either
manual evaluation of the source code or additional scans of the source code itself to assess well.

## Copilot Instruction files that guide GitHub Copilot to creating a useful dependency risk report

_Now back to GitHub Copilot instruction files...._

As noted at the top of this post, we can use instruction.md files to guide GitHub
Copilot to creating higher quality dependency risk report than if we just let it
answer those questions without any guidance.

You can find an example of these instruction files in the repository [microsoft/ospo](https://github.com/microsoft/OSPO/tree/main/.github/instructions) with a explanation
in the [https://github.com/microsoft/OSPO/blob/main/.github/instructions/dependency-risk-README.md](https://github.com/microsoft/OSPO/blob/main/.github/instructions/dependency-risk-README.md). The instruction files for dependency risk are spread
across several different instruction files that are called by a single file.
This approach is used to keep a set of basic instructions that could be
managed in a public repository by a centralized team separate from repository
specific instructions.

### The user experience 

The end result is anytime Copilot suggests a new dependency to use or a developer
asks about the community health of security of a package, a dependency risk report
is created and presented to the user as a report in the chat window.

### Advantages of using Copilot and instruction files as a SAST tool

An advantage of using an instructions file approach to guiding Copilot to surfacing
these risks is that it allows for:
- Project specific flexible cut offs for when a risk is surfaced to the developer rather than a one-size fits all threshold.
- Easy follow up questions by the developer rather than a fixed set of information
- Much faster developer cycle
- Can be used without entering into a contract or paying a vendor
- Information provided in the IDE before the developer writes any code using the dependency

### Disadvantages of using Copilot and instruction files as a SAST tool

- No method exists today to effectively distribute instruction files to many repositories.
    - This is problematic as:
        - Few users will be motivated enough to manually add instruction files for this purpose on their own.
        - Adding the same instructions file for every repository you use is a pain.
        - Developers typically do not like bulk pull requests to their repositories from centralized teams.
        - Even if added once, it is not uncommon for instruction files to evolve over time, often in response to behavior of new models.
- No enforcement mechanism.
    - Users get information, but they can always ignore it. This is not a great compliance methodology.
- Not deterministic
    - Although the risk report worked well in testing with GPT-4o and Claude Sonnet4, other models resulted in occasional hallucination or more creative formatting than was wanted.
- Require hitting APIs, which may not anticipate the increase in traffic.
    - For example, significant parts of the data sourced by the instructions file comes from Ecosyste.ms API, which have a blog post about how the traffic already hitting [their free API](https://blog.ecosyste.ms/2025/09/01/rate-limiting-the-right-way.html) is not sustainable.

## Conclusion

The limitations of this approach mean that is unlikely to be a replacement
for paid enterprise SAST tools. However, it's advantages when it comes to
flexible repository decided thresholds on what levels of risk are acceptable
as well as its better ability to identify and address sustainability risks
may make it an appealing avenue to explore for developers in large companies
that want to make more informed dependency consumption choices or developers
who aren't going to pay for SAST tools but want to apply a bit more risk
filtering earlier in the process than the free options.
